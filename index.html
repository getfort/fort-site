    The problem

    Agents are ready for real systems. Nobody wants to be the one who let them in.

    An agent that can restart a deployment can also delete one. A bad plan, a confused model or a poisoned web page is one tool call away from production, so most agents stay in demos. Fort gives them a place to live where every call is checked against your policy, risky ones wait for a person, and nothing leaves the walls unless you said it could.

    Three core pillars

    Know the agent → Control the agent → Trust the interaction.

    Fort creates trust in your AI agents.

    01 · Trust in identity

    Agent Identity & KYA (Know Your Agent)

    Establish and continuously verify each agent's identity, ownership and accountability.

    • A unique identity for every agent. Authenticated on every action, and running only the version you approved.
    • Clear ownership and accountability. Who owns each agent, who deployed it and who approved its actions is on record.

    Coming soon: model and runtime attestation; provenance; trust & risk scoring.

    Who is this agent, who owns it, and can we trust it?

    02 · Trust in the agent

    Agent Governance & Protection

    Agents operate safely within defined policies and permissions, protected from compromise or manipulation.

    • Policies and permissions you control. Decide which tools and data each agent can use, and what it may do with them.
    • A person approves risky actions. Nothing critical happens until a named person says yes.
    • Contained, even if hijacked. A manipulated agent can still only do what you allow, and one switch stops it instantly.

    Coming soon: prompt-injection and anomaly detection; vulnerability scanning.

    Is this agent operating safely, within its authorized boundaries?

    03 · Trust in interaction

    Secure Communication & Audit

    Secure every exchange between agents and the systems, tools and services they use.

    • The agent never sees a password or key. Credentials are added outside the agent, only where you allow.
    • Every interaction authorized. Each call to a tool or service is checked against your policy, and no agent can pose as another.
    • Tamper-evident audit trail. Every action, allowed or blocked, is recorded as evidence for audit and compliance.

    Coming soon: secure agent-to-agent (A2A) communication.

    Foundation under all three

    The sandbox keeps the agent in. Fort decides what gets out.

    A locked sandbox for every agent. Isolated, with no network of its own. Built on NVIDIA OpenShell.

    How it works

    From an empty VM to a governed agent.

    1. 1

      Raise the walls

      Run fort up on one Linux VM in your cloud. It sets up NVIDIA OpenShell for isolation and starts Fort beside it. Nothing is sent back to us.

    2. 2

      Move your agents in

      Declare each agent as code: its image, its model providers, its tools and its rules. fort apply runs each one in its own sandbox.

    3. 3

      Warden keeps the gate

      Every tool call is checked, argument by argument: allow, ask or deny. An ask waits for a named person to approve from Slack.

    4. 4

      Check the record

      Every call, allowed or not, goes into a hash-chained ledger. fort ledger verify checks it on an auditor's laptop, offline.

    Policy as code

    Rules you can read, review and diff.

    Agents, tools and rules live in a repo and go through review like any other change.

    • A call that matches no rule is denied.
    • Deny beats ask, and ask beats allow.
    • fort explain agent prints what an agent can and can't do, generated from the policy that's enforced.
