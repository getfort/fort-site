Customer deployment · Oracle Cloud

Deploy Fort on
Oracle Cloud.

Fill in your Terraform variables, apply, then open Fort’s operator console and sign in.

Fort runs inside your tenancy. The template provisions a VM in a new dedicated network (or in a public subnet you supply, after checking it), a retained boot volume, a reserved public IP and, in the tenancy, a dynamic group and policy that let that one VM read the one bootstrap secret. The existing console is served by Fort over HTTPS on port 7451. The API and internal services stay private.

Early access. Download the Terraform templates. Ask your Fort contact for qualified binaries; they are supplied separately.

Before you apply. The template has offline validation. A fresh VM, your network, certificates and company sign-in still need qualification in your tenancy; it has not been applied to a live tenancy.

Before Terraform

Prepare your tenancy, hostname
and credentials.

You need Terraform 1.9 or later, below 2.0; OCI credentials authorized to create the resources; an IPv4 source range that can reach the VM; a DNS hostname; a trusted TLS certificate and key; and OIDC clients for company sign-in.

Choose a compartment (a folder of cloud resources in your tenancy), a region and an availability domain (one data centre within the region). Supply the tenancy OCID (Oracle’s resource ID, starting ocid1.tenancy) and the tenancy’s home region (shown under Governance › Tenancy details in the console): identity resources can only be written there, and there is no default, so a wrong guess cannot be applied silently. Select an exact Canonical Ubuntu 24.04 x86_64 image OCID in your region, rather than a moving image name. List the candidates with:

The template creates a dedicated network (a virtual cloud network, VCN, with an internet gateway, route table, a security list with no ingress, and a public subnet) so the VCN’s default security list, which admits SSH from anywhere, never applies. A network security group is the only way in: TCP 7451 from each of your console_cidrs and, if you set them, TCP 22 from each of your ssh_cidrs. To use an existing public subnet instead, set subnet_id; the plan is refused if its security lists already admit SSH, port 7451 or all traffic, because OCI lets either a security list or a network security group open a port. An optional existing public DNS zone gets the hostname’s A record.

The default network is 10.80.0.0/16 with a 10.80.0.0/24 subnet. Avoid overlap with Docker and backend networks. Connecting private backends needs your approved routing. Review inherited tenancy policies separately.

The template also creates, in the tenancy, a dynamic group matching only this VM and a policy allowing it to read secret bundles for the one secret you name. Both are written in the tenancy’s default identity domain, in the home region. The VM signs in with its own OCI identity and holds no key or password. You need rights to manage dynamic groups and policies in the tenancy.

SSH is off by default. If you enable restricted SSH for maintenance, set both ssh_cidrs and ssh_authorized_keys at launch (at most four public keys of 768 characters; the login is ubuntu).

Choose the build

Supply direct HTTPS URLs and separate SHA-256 hashes for fort and fortd from the same qualified Linux x86_64 build. The daemon must include the production console assets. The bootstrap verifies both downloads before execution. Get the hashes from your trusted build process; do not use latest, redirecting links or credentials in URLs.

Prepare the bootstrap secret

Create the secret in an OCI Vault through the console’s protected input or your existing secret-management process. The secret is a JSON object with required tls_certificate (the full PEM chain) and tls_private_key (unencrypted PEM). Optional keys are console_oidc_client_secret and step_up_client_secret; omit unused keys.

The certificate must match your hostname, remain valid for at least a day, and chain to a CA your team’s browsers trust. Terraform takes only the secret’s OCID and an exact version number. Keep private keys and client-secret values out of tfvars, Terraform data sources, VM metadata, command arguments and shell history.

Existing Fort sign-in

Register Fort with your
identity provider.

Choose the hostname first. For fort.company.com, register this exact redirect URI for the browser client:

The issuer must support OIDC discovery and device authorization for CLI sign-in and approval step-up. The console uses authorization code with PKCE. A console session alone cannot finish an approval.

  1. Choose the clients.If one public client supports both grants, use it as oidc_client_id. If your issuer needs separate clients, set the device client there and the web client as console_oidc_client_id. Required secrets belong in the bootstrap secret.
  2. Choose the first administrator.Set admin_group to a group emitted in the configured oidc_groups_claim. Alternatively, set admin_subject to one immutable OIDC sub and omit the group. An email address is not an OIDC subject.
  3. Check issuer and scope.The installer names the issuer default. It binds only the selected group or subject globally to Fort’s admin role and verifies the binding before completing setup.

Creating clients and assigning users remain customer IdP administration.

Reviewable configuration

Fill in one configuration file.

Use the fort-terraform-customer/oci folder from the extracted download, with its sibling shared folder intact. Copy terraform.tfvars.example to terraform.tfvars and replace every placeholder. Each environment needs its own state and resource name.

console_cidrs contains the IPv4 addresses that actually reach Fort, usually your corporate egress ranges. An empty list and a whole-internet CIDR are refused. If you omit the DNS-zone input, add the hostname’s A record yourself using the returned public_ip; do not add an AAAA record.

The defaults are 2 OCPUs (4 vCPUs), 16 GiB and a 120 GiB boot volume. Secure boot (the shielded_instance setting) is off by default; turn it on only after confirming your shape and image support it. Review current regional shape, volume, IP, DNS and Vault pricing. Use your organization’s encrypted, access-controlled Terraform state backend. This single-VM installation does not provide high availability.

OCI limits a VM’s metadata to 32,000 bytes, and the boot script travels compressed inside it. The plan refuses settings that would not fit: URLs are limited to 512 characters, client IDs, audience, claim and administrator fields to 256, the environment name to 64, and SSH keys to four of 768 characters.

Infrastructure, then readiness

Apply and open the console.

Read the plan before applying it. Terraform finishing means the infrastructure exists; the guest installation can still be running or have failed. The dynamic group and policy exist only after the VM, and take a short while to apply, so the first secret read can be refused for a few minutes. The first boot retries only that refusal, for up to ten minutes, then stops and names the dynamic group and policy to check. Look in the instance’s console history (the instance page, or oci compute console-history capture) for Fort bootstrap ready: https://....

Oracle’s Ubuntu images also block inbound ports in the VM itself. The boot adds one saved firewall rule for port 7451 and changes nothing else. The bootstrap then uses the existing fort up installer, fetches TLS and client secrets by reference, and confirms the admin binding. Completion requires healthy Fort/OpenShell services, fort doctor and real console assets. It never prints the temporary bootstrap token.

  1. Open the returned HTTPS URL.Use an allowed network and check the certificate without a browser exception. The URL includes :7451.
  2. Sign in with company SSO.Confirm the selected administrator can access Agents and Access. An unassigned account must not gain admin.
  3. Verify the boundaries.Check that API/internal ports are closed externally, disallowed sources cannot reach the console or SSH, and approval decisions still require a separate human step-up.

Adding model-provider keys remains a CLI operation; the console does not accept secret values. Continue with agent and tool-server setup ↗ after installation is verified.

After the console is ready

Deploy the agent
and its tools.

The template installs Fort and its console. Next, prepare an agent image and the tool-server images it will call. Backend operations and their credentials belong in tool servers outside the agent sandbox.

Fort runs declared tool servers in separate Docker containers on the same Fort VM. Declare their images, backend secrets, health checks and tool policy, then configure the agent’s MCP client to use Fort’s injected tool URL. fort apply deploys and maintains the containers.

Finish onboarding with a healthy tool server and one successful, allowed read-only call from the agent to the backend. A running VM or sandbox alone does not prove this path works.

After installation

Keep evidence safe
through maintenance.

Retry an unchanged failed bootstrap with sudo python3 /var/lib/fort-onboarding/oci_bootstrap.py through an approved root administration path. The error identifies its stage without exposing upstream command or secret payloads. A completed unchanged install is a no-op; changed configuration is refused. If the stage is the secret read, check the dynamic group and policy first.

If the temporary bootstrap token expired before the administrator was bound, inspect the installation and reissue into root’s credential store with sudo env -u SUDO_UID -u SUDO_GID -u SUDO_USER HOME=/root /usr/local/bin/fort up --reissue-bootstrap-token before retrying. Clearing the sudo caller variables is essential: setting HOME alone still delivers the new token to the SSH operator, while the bootstrap reads root’s credentials. Do not reissue credentials for unrelated failures.

For TLS renewal or client-secret rotation, use a maintenance window and your approved root-only secret retrieval process. Atomically replace the relevant files under /etc/fort/customer, preserving fort ownership, certificate mode 0644 and key/client-secret mode 0600. For device-secret rotation, explicitly reinstall the installed copy with sudo fort up --step-up-client-secret-file /etc/fort/customer/device.secret; plain fort up preserves its old copy. For certificate or console-client secret changes, run sudo fort up with its recorded settings. Explicitly run sudo systemctl restart fortd to load the new TLS and browser-client secret, then sudo fort doctor, service checks and browser sign-in/step-up checks. Restarting Fort ends browser sessions, and governed calls fail closed during the restart. Rotation is explicit maintenance; changing tfvars does not replay the original bootstrap, and a changed boot script is not applied to an installed VM.

The VM has Terraform prevent_destroy, and its boot volume is kept if the VM is terminated. Before replacement, create and verify a Fort backup, copy it off-host and test restore. A retained volume is not a backup.

Intentional replacement or deletion requires a reviewed change removing Terraform’s protection. Record the retained boot volume’s identity, then delete it separately only after confirming your evidence-retention policy and off-host backups. The dynamic group and policy are separate tenancy resources to remove afterwards. Stopped VMs still incur volume and IP charges. Do not suspend a running Fort VM.
