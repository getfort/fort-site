Early-access deployment · Oracle Cloud

Deploy Fort on
Oracle Cloud.

Download the templates, configure your tenancy and sign in to Fort.

One VM in your Oracle Cloud Infrastructure (OCI) tenancy, with a retained boot volume and a reserved IP. HTTPS console access is restricted to your network on port 7451; internal services stay private. This is a single-VM installation, without high availability.

Download Terraform templates ↓

AWS + Google Cloud + Oracle Cloud · includes shared bootstrap and operating reference · SHA-256 checksum. Qualified Fort binaries are supplied separately by your Fort contact. These templates have offline validation; qualify the VM, network, TLS and sign-in in your tenancy.

1. Have these ready.

  • Terraform ≥ 1.9 and < 2.0, OCI credentials and an encrypted, access-controlled state backend. Review cloud costs.
  • A compartment (the folder in your tenancy that will hold Fort), a region, your tenancy’s home region (shown under Governance › Tenancy details) and an exact Canonical Ubuntu 24.04 x86_64 image OCID (an OCID is Oracle’s resource ID). The module creates a dedicated network; check range overlap and tenancy policies.
  • Rights to manage dynamic groups and policies in the tenancy. The module creates both, so the VM can read one secret and nothing else.
  • A DNS hostname, trusted matching TLS certificate/key and a bootstrap secret in an OCI Vault, with its OCID and an immutable version number (shown on the secret’s Versions list).
  • Company SSO: an OIDC issuer with discovery, device authorization and browser authorization-code + PKCE; client IDs and a first administrator group or immutable subject.
  • Direct HTTPS URLs and trusted SHA-256 hashes for fort and fortd from the same qualified Linux x86_64 build, including console assets.

Register https://YOUR_HOSTNAME:7451/auth/callback for the browser client. SSO setup is required before applying. Client and administrator setup ↗ · Secret format and cloud prerequisites ↗

2. Configure the template.

Extract the ZIP and keep aws, gcp, oci and shared together. In fort-terraform-customer/oci, copy the example:

Replace every placeholder: tenancy, compartment, region and home region, availability domain, image, bootstrap-secret OCID and version, allowed console_cidrs (the IP ranges that may open the console), hostname, binary URLs/hashes, OIDC clients and administrator. The example documents each field; see the full configuration reference.

Keep private keys and client-secret values in the Vault secret, never in tfvars, policy, command arguments or VM metadata. Use your actual IPv4 egress ranges; whole-internet access is refused. SSH is closed by default; arrange an approved maintenance path before launch.

3. Review, apply and open Fort.

If you did not set a DNS-zone input, point your hostname’s A record at terraform output -raw public_ip; do not add an AAAA record.

Terraform completion is not installation readiness. The VM’s access to its secret appears a few minutes after the VM does, so the first boot retries for up to ten minutes before it stops and names the dynamic group and policy to check. Wait for Fort bootstrap ready: https://... in the instance’s console history. Then open the returned HTTPS URL from an allowed network, check TLS without an exception and sign in with the configured SSO administrator.

Confirm Agents and Access are available, unassigned users have no admin access, and internal ports remain private. Approval decisions require a separate human step-up. Readiness checks ↗

4. Connect your first agent.

Prepare separate agent and tool-server images. Backend credentials belong in the tool server, outside the agent sandbox. Configure the agent’s MCP client, then verify one allowed read-only call and its ledger decision.
