Customer deployment · AWS

Deploy Fort on
AWS.

Fill in your Terraform variables, apply, then open Fort’s operator console and sign in.

Fort runs inside your cloud. The template provisions an EC2 VM in an existing public subnet, an encrypted retained disk, a stable Elastic IP, a dedicated security group and a narrowly scoped VM role. The existing console is served by Fort over HTTPS on port 7451. The API and internal services stay private.

Early access. Download the Terraform templates. Ask your Fort contact for qualified binaries; they are supplied separately.

Before you apply. The template has offline validation. A fresh VM, your network, certificates and company sign-in still need qualification in your environment.

Before Terraform

Prepare your cloud, hostname
and credentials.

You need Terraform 1.9 or later, below 2.0; cloud credentials authorized to create the resources; an IPv4 source range that can reach the VM; a DNS hostname; a trusted TLS certificate and key; and OIDC clients for company sign-in.

Choose an existing VPC and public subnet with an internet-gateway route and working DNS. Select a pinned Canonical Ubuntu 24.04 amd64 AMI in the same region (owner 099720109477). Supply an existing Secrets Manager secret ARN and its immutable VersionId.

The VM role can read that secret only. If it uses a customer-managed KMS key, supply the exact key ARN and permit the created role in that key’s policy. An optional existing Route 53 public hosted zone gets an A record for your hostname.

SSH is off by default. Check your subnet’s NACL and organization policies before deployment.

Choose the AWS administration path before launch. For SSH, set key_name initially while ssh_cidrs stays empty, then temporarily enable the approved CIDRs when needed. Adding or changing the EC2 key later requires VM replacement and is blocked by prevent_destroy. The template does not provision an alternative administration service such as SSM.

Choose the build

Supply direct HTTPS URLs and separate SHA-256 hashes for fort and fortd from the same qualified Linux x86_64 build. The daemon must include the production console assets. The bootstrap verifies both downloads before execution. Get the hashes from your trusted build process; do not use latest, redirecting links or credentials in URLs.

Prepare the bootstrap secret

Use your cloud’s protected secret input or existing secret-management process. The secret is a JSON object with required tls_certificate (the full PEM chain) and tls_private_key (unencrypted PEM). Optional keys are console_oidc_client_secret and step_up_client_secret; omit unused keys.

The certificate must match your hostname, remain valid for at least a day, and chain to a CA your team’s browsers trust. Terraform takes only the secret reference and exact version. Keep private keys and client-secret values out of tfvars, Terraform data sources, VM metadata, command arguments and shell history.

Existing Fort sign-in

Register Fort with your
identity provider.

Choose the hostname first. For fort.company.com, register this exact redirect URI for the browser client:

The issuer must support OIDC discovery and device authorization for CLI sign-in and approval step-up. The console uses authorization code with PKCE. A console session alone cannot finish an approval.

  1. Choose the clients.If one public client supports both grants, use it as oidc_client_id. If your issuer needs separate clients, set the device client there and the web client as console_oidc_client_id. Required secrets belong in the bootstrap secret.
  2. Choose the first administrator.Set admin_group to a group emitted in the configured oidc_groups_claim. Alternatively, set admin_subject to one immutable OIDC sub and omit the group. An email address is not an OIDC subject.
  3. Check issuer and scope.The installer names the issuer default. It binds only the selected group or subject globally to Fort’s admin role and verifies the binding before completing setup.

Google sign-in needs a Web application client for the console and a separate TVs and Limited Input devices client for device flow. Put their required secrets in the corresponding bootstrap-secret fields. Creating clients and assigning users remain customer IdP administration.

Reviewable configuration

Fill in one configuration file.

Use the fort-terraform-customer/aws folder from the extracted download, with its sibling shared folder intact. Copy terraform.tfvars.example to terraform.tfvars and replace every placeholder. Each environment needs its own state and resource name.

console_cidrs contains the IPv4 addresses that actually reach Fort, usually your corporate egress ranges. An empty list and a whole-internet CIDR are refused. If you omit the DNS-zone input, add the hostname’s A record yourself using the returned public_ip; do not add an AAAA record.

The defaults are 4 vCPU, 16 GiB and a 120 GiB disk. Review current regional VM, disk, IP, DNS and secret-access pricing. Use your organization’s encrypted, access-controlled Terraform state backend. This single-VM installation does not provide high availability.

Infrastructure, then readiness

Apply and open the console.

Read the plan before applying it. Terraform finishing means the infrastructure exists; the guest installation can still be running or have failed. Look in EC2 system/console output for Fort bootstrap ready: https://....

The bootstrap uses the existing fort up installer, fetches TLS and client secrets by reference, and confirms the admin binding. Completion requires healthy Fort/OpenShell services, fort doctor and real console assets. It never prints the temporary bootstrap token.

  1. Open the returned HTTPS URL.Use an allowed network and check the certificate without a browser exception. The URL includes :7451.
  2. Sign in with company SSO.Confirm the selected administrator can access Agents and Access. An unassigned account must not gain admin.
  3. Verify the boundaries.Check that API/internal ports are closed externally, disallowed sources cannot reach the console or SSH, and approval decisions still require a separate human step-up.

Adding model-provider keys remains a CLI operation; the console does not accept secret values. Continue with agent and tool-server setup ↗ after installation is verified.

After the console is ready

Deploy the agent
and its tools.

The template installs Fort and its console. Next, prepare an agent image and the tool-server images it will call. Backend operations and their credentials belong in tool servers outside the agent sandbox.

Fort runs declared tool servers in separate Docker containers on the same Fort VM. Declare their images, backend secrets, health checks and tool policy, then configure the agent’s MCP client to use Fort’s injected tool URL. fort apply deploys and maintains the containers.

Finish onboarding with a healthy tool server and one successful, allowed read-only call from the agent to the backend. A running VM or sandbox alone does not prove this path works.

After installation

Keep evidence safe
through maintenance.

Retry an unchanged failed bootstrap with sudo python3 /var/lib/fort-onboarding/bootstrap.py through an approved root administration path. The error identifies its stage without exposing upstream command or secret payloads. A completed unchanged install is a no-op; changed configuration is refused.

If the temporary bootstrap token expired before the administrator was bound, inspect the installation and reissue into root’s credential store with sudo env -u SUDO_UID -u SUDO_GID -u SUDO_USER HOME=/root /usr/local/bin/fort up --reissue-bootstrap-token before retrying. Clearing the sudo caller variables is essential: setting HOME alone still delivers the new token to the SSH operator, while the Python bootstrap reads root’s credentials. Do not reissue credentials for unrelated failures.

For TLS renewal or client-secret rotation, use a maintenance window and your approved root-only secret retrieval process. Atomically replace the relevant files under /etc/fort/customer, preserving fort ownership, certificate mode 0644 and key/client-secret mode 0600. For device-secret rotation, explicitly reinstall the installed copy with sudo fort up --step-up-client-secret-file /etc/fort/customer/device.secret; plain fort up preserves its old copy. For certificate or console-client secret changes, run sudo fort up with its recorded settings. Explicitly run sudo systemctl restart fortd to load the new TLS and browser-client secret, then sudo fort doctor, service checks and browser sign-in/step-up checks. Restarting Fort ends browser sessions, and governed calls fail closed during the restart. Rotation is explicit maintenance; changing tfvars does not replay the original bootstrap.

The VM has Terraform prevent_destroy and EC2 termination protection. Its encrypted root disk is retained if the VM is deliberately deleted. Before replacement, create and verify a Fort backup, copy it off-host and test restore. A retained disk is not a backup.

Intentional replacement or deletion requires a reviewed change removing Terraform’s protection and disabling the cloud protection. Record the retained disk identity, then delete that disk separately only after confirming your evidence-retention policy and off-host backups. Stopped VMs still incur disk/IP charges. Do not suspend a running Fort VM.
